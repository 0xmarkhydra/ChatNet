## Implemented in this batch

1. Removed the short-lived Gemini translation access ticket from the browser WebSocket URL. It is now sent as the first WebSocket message over the encrypted connection. The server rejects query credentials and accepts only allowed browser origins. Tickets are still single-use with Redis GetDel and short TTL.
2. Added periodic backend authorization checks for **both** listener and speaker while Gemini audio processing is active. When either participant loses call access, the AI stream terminates independently; the LiveKit call is not disconnected by this guard.
3. Corrected Gemini 3.5 Live Translate setup according to the **official Google Live Translation guide**: input/output transcription configuration belongs inside `generationConfig`, alongside `translationConfig`.
4. Made speaker identity validation exact: `u_<positive integer>`, rejecting suffixes or malformed IDs.
5. Categorized Gemini HTTP 429 and 401/403/setup failures into user-friendly quota/access errors without sending provider details or API keys to the browser.
6. Added backend regression tests for invalid ticket URLs, untrusted origins, model setup nesting, identity validation and safe AI errors.

Official API reference: https://ai.google.dev/gemini-api/docs/live-api/live-translate

## Follow-up batch — authenticated voice consent

- `GET /api/calls/{id}/translation-consent` reads **only the authenticated joined speaker's** consent from Redis; `POST /api/calls/{id}/translation-consent` with `{"allowed":true|false}` grants/revokes only the user's own permission. Strict JSON validation, authorization, 20/min rate limit, no-store response, call/speaker-scoped Redis key and max 2-hour TTL.
- Before ticket issuance, on WebSocket ticket consumption and every 2 seconds of an active Gemini stream, backend confirms speaker consent. Fail-closed on missing/expired/failed Redis reads and on participant departure. AI stream is stopped independently of the LiveKit call.
- On every LiveKit join, speaker consent is reset (including rejoins, requiring a new explicit grant). When a member declines/leaves or a call ends, server deletes available consent keys; periodic auth checks still guard unexpected membership changes. If Redis is unavailable during cleanup, server reports a sanitized error and translation access subsequently fails closed while Redis is unavailable.
- Browser one-click consent now calls real backend before broadcasting LiveKit consent to listeners; GET synchronizes on call join. Revocation is reflected immediately in UI; if backend cannot confirm withdrawal, microphone disable is attempted with visible warning.
- Browser UI now explicitly explains that decrypted audio is processed by **ChatNet server and Google Gemini**; audio is not silently uploaded and no transcript retention has been added.
- No database migration. **New API dependency:** frontend/backend must be deployed together; old clients using only LiveKit data-channel consent can no longer start translation without the POST grant.
- Note: a backend permission grant authorizes Gemini audio processing for this call, not broader access to the microphone. This does **not** establish an independent E2E proof of user consent.

## Follow-up batch — joined-member E2EE key relay and reconnect safety

- E2EE public-key and wrapped-envelope access now requires an **actively joined**, not-left, not-declined call participant who still belongs to the underlying conversation. The key list excludes those who have left or lost conversation membership; wrapped keys cannot be issued to an inactive recipient.
- When a group member leaves, the backend checks and persists the DB update instead of ignoring failures, revokes their cached relay keys and AI consent, then requests removal of their LiveKit participant with a **room-scoped admin grant**. A LiveKit RPC failure is logged without leaking secrets; this is still a release blocker to exercise on staging.
- While LiveKit is reconnecting/disconnected, the React call room stops and cleans up active AI translation sessions. It may restart after `RoomEvent.Reconnected` when the stream is connected and speaker consent is present.
- Added a unit test to inspect the room-scoped LiveKit removal JWT permissions, and static checks that the UI reconnect guard and joined-key paths remain present.
- **Security limitation:** Token lifetime and group E2EE shared-key rotation/removal need adversarial live testing; kicking a LiveKit participant and blocking relay endpoints alone do not prove expired JWT or old media keys are immediately invalidated. No production-readiness claim.

## Follow-up patch — no ghost rejoin after group leave

- `GET /api/calls/current` now filters `call_participants.left_at IS NULL` as well as non-declined participant status. Previously, a joined group member who left could still be returned as an active call and be reopened by the React refresh/SSE flow.
- The query is now a named constant with a regression test asserting departed/declined and removed conversation members are excluded by its predicates. SQL integration tests with a live PostgreSQL fixture are still pending.
